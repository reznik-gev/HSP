# 0033 — Audit logging: application-level audit table

- **Date:** 2026-10-08
- **Status:** Accepted

## Options considered
- **App-level audit table** ✅
- DB triggers writing to history tables
- Both

## Decision
- A single append-only **`audit_event`** table, written by the service layer **in the same transaction** as the change.
- Columns: `id` (UUIDv7), `tenant_id`, `occurred_at`, `actor_person_id` / `actor_subject` (Keycloak `sub`), `action` (e.g. `seat.assigned`, `floor.published`, `person.imported`), `entity_type`, `entity_id`, `before` / `after` (JSONB, changed fields only), `request_id`, optional `reason`.
- Floor-plan edits are **not** audited per element. The version history ([0028](0028-2026-10-08-floor-version-storage.md)) already records them. Version-level events (lock acquired or force-released, publish, discard, restore) are audited.

## Consequences
- Answers "who changed what, when, and why" with full request context.
- Seat-assignment history ([0031](0031-2026-10-08-seat-assignment-rules.md)) is queried from `audit_event`, which is indexed on `(tenant_id, entity_type, entity_id, occurred_at)`.
- Changes made outside the app (manual SQL) are not captured. Operators are expected not to change data directly. Triggers can be added later if compliance requires it.
- The application database role has no `UPDATE` or `DELETE` grant on `audit_event`. Retention and archiving policy is decided later.
