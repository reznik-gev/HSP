# 0010 — Backend stack: Python + FastAPI

- **Date:** 2026-10-08
- **Status:** Accepted

## Context
We need a backend language and framework for the from-scratch build ([0002](0002-2026-10-07-build-approach.md)), deployed on-prem ([0005](0005-2026-10-07-deployment-model.md)).

## Options considered
- TypeScript / NestJS: could share code with the front end.
- C# / ASP.NET Core: strong typing, a good fit for Windows shops.
- **Python / FastAPI** ✅: chosen by the product owner.
- Python / Django: **explicitly rejected.**
- Go: small binaries, but more boilerplate for domain logic.

## Decision
The backend is written in **Python with FastAPI**. Django is not used.

## Known cons and mitigations
| Con | Mitigation |
|---|---|
| FastAPI is a micro-framework, so ORM, migrations, jobs, admin and settings must be assembled | Choose these in a follow-up decision. Define the project layout and conventions early. |
| No code shared with the TS/JS front end (geometry and unit rules exist twice) | The server is the source of truth for geometry. Generate the TS client and types from OpenAPI. |
| The GIL limits CPU-bound geometry | Push spatial work to the database (PostGIS) or Shapely/GEOS. Run several worker processes. |
| Async pitfalls (blocking calls, lazy-load errors) | Async-only database access, explicit eager loading, lint rules for blocking calls. |
| Dynamic typing in a complex domain | `mypy --strict` or pyright strict, Pydantic v2 at boundaries, enforced in CI. |
| On-prem packaging (image size, native deps, offline installs) | `uv` with a lockfile, multi-stage slim images, vendored wheels for air-gapped installs. |
| Maintainer concentration in FastAPI | Keep framework-specific code thin in the HTTP layer. The domain and services stay framework-agnostic. |
| Multi-worker real-time collaboration needs a broker | Decide when we design live editing. Redis pub/sub is the likely default. |

## Consequences
- Supporting libraries (ORM, migrations, background jobs, admin UI, tooling) are decided in a follow-up record.
- The OpenAPI schema is a first-class build artifact that the front end consumes.
