# 0106 — Backups: our own image, with schedules in `backups.yml`

- **Date:** 2026-10-21
- **Status:** Accepted
- **Refines:** [0058](0058-2026-10-08-backups.md) (backups)

## Context
[0058](0058-2026-10-08-backups.md) chose scheduled dumps of the HSP and Keycloak databases to a folder or S3, with a weekly restore test. Nothing is built yet. The owner wants the schedules configurable, not fixed to "7 daily and 4 weekly": a list of schedules, each with its own options. Folder and S3 are both needed.

## Options considered
The owner chose each of these:

| Question | Options | Chosen | Why |
|---|---|---|---|
| What runs the backups | **Our own small image** / shell with supercronic and rclone / an off-the-shelf image | **Our own image** | Python like the API, unit-tested, with exactly the config and metrics we need. |
| Where schedules are set | **A `backups.yml` file** / numbered variables in `.env` | **`backups.yml`** | Lists of schedules and nested S3 options read naturally in YAML, not in flat variables. |
| What the weekly restore test covers | Folder and S3 (MinIO) / **the folder only** / only inside the release test | **The folder only** | Faster. S3 is covered by unit tests against a fake. |

**To research later (the owner's note):** whether an off-the-shelf backup image, or a third-party backup service, can take this responsibility off us. Owning and testing the code isn't the cost. The cost is the edge cases we might miss and the features we don't offer, such as encryption, incremental backups and more targets. Revisit when a customer asks for something the image doesn't do, or before backups grow beyond this record.

## Decision
1. **`hsp-backup`**, a new image: a short Python program on the PostgreSQL 18 client image, run as the `backup` service in the Compose stack and shipped in the bundle. It schedules with cron expressions (croniter), runs `pg_dump`, writes to a folder or to S3 (boto3, so MinIO and other S3-compatible stores work), deletes old backups, and serves its own metrics.
2. **`backups.yml`**, next to `compose.yml`, holds **named targets** and a **list of schedules**:
   ```yaml
   timezone: Asia/Jerusalem
   targets:
     local:   { type: folder, path: /backups }
     offsite: { type: s3, endpoint: https://minio.corp:9000, bucket: hsp-backups, prefix: prod/,
                region: us-east-1, path_style: true, ca_file: /etc/hsp/backup-ca.pem }
   schedules:
     - { name: nightly, cron: "30 2 * * *", target: local,   keep: 7 }
     - { name: weekly,  cron: "0 4 * * 0",  target: offsite, keep: 8, keep_days: 90, include_config: true }
   manual: { target: local, keep: 5 }
   ```
   It's checked at start, and the service refuses to run with a bad file, naming the problem. `hsp install` writes a default that matches 0058: 7 nightly and 4 weekly to `$HSP_DATA_DIR/backups`.
3. **One backup is one file**, `hsp-<UTC time>-<schedule>.tar`, holding:
   - `hsp.dump` and `keycloak.dump` (`pg_dump` custom format, compressed)
   - `manifest.json`: the HSP version, schema revision, time, schedule and checksums
   - with `include_config: true`, the installation's `.env`, `backups.yml` and `compose.yml`. **Never `secrets/`.**

   A folder backup is written under a temporary name and then renamed. An S3 backup is uploaded and then checked. A half-written backup never counts.
4. **Keeping backups:** each schedule keeps its newest `keep` backups on its target, counted per schedule, so hourly backups never delete weekly ones. With `keep_days` as well, whichever keeps more wins. Manual backups (`hsp backup now`) keep the last 5 by default. Pre-upgrade backups ([0056](0056-2026-10-08-upgrades-and-migrations.md)) are kept until the next successful upgrade.
5. **Failures:** a failed run logs an error, deletes its partial file and waits for the next scheduled time, with no retries. If a run is still going when the next is due, the new one is skipped and logged.
6. **Metrics** on the backup service's own port, `HSP_BACKUP_METRICS_PORT` (9465), on `HSP_METRICS_ADDRESS` like the API's ([0105](0105-2026-10-21-metrics-and-tracing.md)). Per schedule: the last success and failure times, duration and size. Alerting on backup age (0058) is the operator's Prometheus.
7. **Commands inside the image**, used by `bin/hsp` ([0107](0107-2026-10-21-operator-cli.md)): `hsp-backup now`, `list`, `restore <backup>` and `check` (validates `backups.yml`).
8. **Restore** replaces both databases from a backup into a stopped stack. It refuses a backup made by a **newer** HSP version than the one installed. An older one is fine: `migrate` brings it up to date on start.
9. **S3 keys** come from the secret files `backup_s3_access_key` and `backup_s3_secret_key`. `path_style` suits MinIO, and `ca_file` suits endpoints with an internal certificate authority.
10. **Tests:**
    - Unit tests, with a fake S3 (moto) for the S3 target.
    - A **weekly CI workflow** (and by hand): build the images from `main`, install and seed a stack, `hsp backup now` to a folder, `hsp restore` into a fresh stack, then check row counts, sign-in and a seat search. It also runs on PRs that change the backup code or the workflow.

## Consequences
- The backup service signs in to PostgreSQL as the superuser, because it dumps and restores both databases.
- Backups hold personal data. Encrypting the target stays the operator's job, as 0058 says.
- S3 is tested end to end only by customers' real use until a test against MinIO is added.
- Customers on AWS with instance roles must still use keys for now.
