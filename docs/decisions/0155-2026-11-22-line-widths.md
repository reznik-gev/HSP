# 0155 — Comments in scripts and config files wrap at 100 characters, written down but not checked

- **Date:** 2026-11-22
- **Status:** Accepted
- **Refines:** [0062](0062-2026-10-08-code-quality-tooling.md) (line widths the tools don't set)

## Context
Ruff sets the width of Python lines, at 120 ([0151](0151-2026-11-21-python-lines-may-be-120-characters-long.md)), and Prettier sets the width of frontend code, at 100. The commit-msg hook allows a summary line of at most 100 characters ([0148](0148-2026-11-18-every-commit-message-has-a-body.md)). No tool sets a width for shell scripts or config files: `.yml`, Dockerfiles, `.env.example`, the nginx files and `deploy/bin/musical-chairs`.

In those files, comments have been wrapped at 100 by habit, and long code lines left whole. The owner confirmed this in the rename's review (#182): code lines may stay long, but comments are wrapped. The rename's longer name pushed 28 comment lines in config files over 100, and #188 wrapped them again. Only the review bot noticed. The rule wasn't written anywhere a session or the bot could read it.

On 2026-11-22, no comment line in these files is over 100 characters. 767 code lines are.

## Options considered
**Checking it:**
- **Written down only** ✅. Review catches a line that goes over.
- A CI check: a small script that fails on a comment line over 100. It would pass today and catch drift, but it's one more thing to maintain for a rule that rarely breaks.
- `max_line_length` in `.editorconfig`: some editors would then hard-wrap code lines too, which the rule keeps whole.

**Where it's written:**
- **A short guide that lists every line width in one place** ✅, linked from CLAUDE.md.
- A line in each side's README: shell and config files belong to neither side.

## Decision
- **In shell scripts and config files, comments wrap at 100 characters. Code lines aren't split to fit.** *(The owner's choice, in #182's review)*
- **It's written down, not checked by CI or a hook.** *(The owner's choice)*
- **When a rename or other edit pushes a comment past 100, rewrap the whole comment paragraph,** keeping code in backticks in one piece. *(Claude's choice, as #188 did)*
- **The other widths stay as they are, and the guide lists them:** Python lines 120, checked by Ruff ([0151](0151-2026-11-21-python-lines-may-be-120-characters-long.md)); frontend code 100, set by Prettier; a commit's summary line 100, checked by the hook ([0148](0148-2026-11-18-every-commit-message-has-a-body.md)); Markdown has no width, and a paragraph is one line. *(Claude's choice)*
- **This rule doesn't cover TypeScript comments.** Prettier doesn't wrap comments or strings, and 60 comment lines in the frontend are over 100 today. *(Claude's choice)*
- **The list is a new guide, [line widths](../guides/line-widths.md),** in the guides index and in CLAUDE.md's "Read these first". *(Claude's choice)*

## Consequences
- Sessions and the review bot can find the rule, and point to it in a review.
- A comment line that goes over 100 is caught only in review. If that turns out to happen often, a CI check is the next step, with a new record.
