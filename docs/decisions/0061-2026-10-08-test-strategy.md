# 0061 — Test strategy: mostly mocked DB, targeted DB integration tests

- **Date:** 2026-10-08
- **Status:** Accepted

## Options considered
- Testcontainers (real PostGIS for every DB-touching test)
- Shared compose test stack
- **Mostly mocked DB** ✅

## Decision
**Backend:**
- **Unit tests (the majority):** services and domain logic are tested against **mocked or in-memory repositories**. They are fast, need no Docker, and run on every save.
- **DB integration tests (deliberately few, but mandatory).** They run against a real PostGIS (a GitHub Actions service container in CI, the dev compose database locally). They cover exactly what mocks *cannot* verify:
  1. Every Alembic migration, applied to an empty DB **and** to a DB seeded with the previous release's schema ([0056](0056-2026-10-08-upgrades-and-migrations.md))
  2. The version-range exclusion constraint and the draft edit, publish and discard queries ([0028](0028-2026-10-08-floor-version-storage.md))
  3. The whole-mm grid `CHECK` constraints ([0029](0029-2026-10-08-geometry-representation.md))
  4. Seat assignment uniqueness and the holder `CHECK` ([0031](0031-2026-10-08-seat-assignment-rules.md))
  5. PostGIS spatial queries: zone containment and nesting, innermost-zone lookup ([0020](0020-2026-10-08-space-hierarchy.md))
  6. Cursor pagination queries ([0040](0040-2026-10-08-pagination.md)) and tenant scoping ([0003](0003-2026-10-07-tenancy-model.md))
- **Shared validation cases** (`/shared/validation-cases`) run in both backend and frontend suites ([0051](0051-2026-10-08-validation-feedback.md)).

**Frontend:**
- Vitest unit tests for the **headless editor core**: tools, snapping, hit-testing, operations and inverses ([0050](0050-2026-10-08-undo-redo.md), [0052](0052-2026-10-08-svg-commitment-and-performance-gate.md)), plus property-based tests for undo.
- Component tests with mocked API responses (MSW).

**End-to-end:** a small Playwright smoke suite against the full compose stack (login, draw, publish, assign) is planned. Its scope is decided when the first features exist.

## Consequences
- Fast feedback for most code, with no Docker needed for most backend tests.
- **Risk:** behavior that depends on Postgres but isn't on the list above can slip through mocks. **Rule:** any new DB constraint, trigger or non-trivial query (raw SQL, PostGIS, window functions) must come with an integration test, and code review checks this.
- Repositories must stay thin, with logic in services, so that mocking them is meaningful.
