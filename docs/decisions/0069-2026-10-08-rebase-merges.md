# 0069 — Merge method: rebase only, linear history

- **Date:** 2026-10-08
- **Status:** Accepted
- **Supersedes:** the "squash merge" part of [0064](0064-2026-10-08-branching-workflow.md). The rest of 0064 (trunk-based, PRs, required checks, tags, `release/X.Y` hotfix branches) stands.

## Options considered
- Squash only (as recorded in 0064)
- **Rebase only** ✅ (the product owner dislikes both squash merges and merge commits)
- All methods allowed

## Decision
- Pull requests into `main` are merged **only by rebase**. The ruleset allows only the `rebase` merge method and **requires linear history**, and the repository disables merge commits and squash merging.
- Each commit of a PR lands on `main` **unchanged**, so `main` reads as the sequence of individual commits.

## Consequences
- **Commit hygiene matters.** Every commit in a PR becomes permanent history:
  - Each commit should be one logical change with a clear message. Clean up "fix typo" or "wip" commits with an interactive rebase/fixup **before** merging.
  - Each commit should ideally pass CI on its own, which keeps `git bisect` useful. CI only verifies the PR head, so this is a convention, not something CI enforces.
- `Co-Authored-By` trailers and per-commit messages are preserved, unlike with squash.
- Rebased commits get new SHAs on `main`, so the PR branch's SHAs won't appear on `main`. This is normal: delete merged branches rather than reusing them.
- With "require branches to be up to date" on, a PR may need re-rebasing onto `main` before merge (GitHub's "Update branch → Rebase" button, or `git pull --rebase origin main` locally).
