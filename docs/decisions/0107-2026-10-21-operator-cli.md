# 0107 — `bin/hsp`: a thin bash script on the Docker host

- **Date:** 2026-10-21
- **Status:** Accepted
- **Refines:** [0054](0054-2026-10-08-release-distribution.md) (the bundle), [0056](0056-2026-10-08-upgrades-and-migrations.md) (upgrades), [0102](0102-2026-10-19-release-workflow.md) (the upgrade test)

## Context
[0054](0054-2026-10-08-release-distribution.md) put an operator command, `bin/hsp`, in the bundle, for installing, upgrading, backing up and restoring. It doesn't exist yet: installing is a page of manual steps in `deploy/README.md`. The owner asked whether it could also run from a Windows workstation that manages Docker hosts or Kubernetes remotely.

## Options considered
The owner chose each of these:

| Question | Options | Chosen | Why |
|---|---|---|---|
| What it's written in | **Thin bash on the host** / Python on the host / a bash shim running an ops container / a cross-platform CLI for remote use | **Thin bash on the host** | It needs nothing beyond what HSP already requires: Docker with Compose, and a shell. Remote use from any workstation is `ssh host sudo hsp …`. Real logic lives in our Python images. Remote management and Kubernetes come right after 1.0 ([0104](0104-2026-10-21-v1-release-scope-and-support.md)). |
| What the upgrade test upgrades from | **The last release only** / the last release, or the same build until one exists / also from the oldest supported | **The last release only** | 1.0.0 has nothing before it, so the test starts with the first release after it. Before 1.0.0, upgrade and rollback are tried by hand. |
| Old images after an upgrade | Remove all but the previous version / **keep them all** | **Keep them all** | The operator decides when to prune. Each version takes about 0.7 GB of disk. |

## Decision
`bin/hsp` is one bash script, checked by shellcheck, copied into the installation folder by `hsp install`. It runs as root on the Docker host and drives Docker and Compose. Anything with real logic, such as backups, runs inside our images.

| Command | What it does |
|---|---|
| `hsp install <bundle> [--dir /opt/hsp]` | Refuses if the folder already holds an installation. Asks for the public URL and TLS mode, or takes `--public-url` and `--tls` for scripted installs. Checks the checksums, loads the images, writes `.env` and a default `backups.yml` ([0106](0106-2026-10-21-backups.md)), creates the secrets with the right owners, and starts the stack. Then it waits until every service is healthy, and creates the first admin: it asks for a name and email, and prints a one-time password to change at first sign-in. |
| `hsp upgrade <bundle>` | Refuses a downgrade or skipping a MAJOR ([0063](0063-2026-10-08-release-versioning.md)). Then the steps of [0056](0056-2026-10-08-upgrades-and-migrations.md): check the checksums, load the images, take a pre-upgrade backup (abort if it fails), and stop `api`, so nginx answers "being updated". Then migrate, start the new version and wait for `/readyz`. The new `compose.yml` replaces the old one. `.env` keeps every value already set, gains new settings with their defaults, and the changes are printed. The previous compose files are kept for rollback. Old images are never removed. |
| `hsp rollback` | Restores the pre-upgrade backup and starts the previous version's images and compose files. |
| `hsp status` | The installed version, each service's state and health, the last successful backup per schedule and any failure since, and free disk in `HSP_DATA_DIR` and the backup folder. |
| `hsp backup now` / `hsp backup list` | Run `hsp-backup now` / `list` in the backup service. |
| `hsp restore <backup>` | Asks for confirmation, stops the stack, runs `hsp-backup restore`, and starts it again. |

**Tests:** shellcheck in CI. The release test installs the bundle with `hsp install` instead of the manual steps. The weekly restore test ([0106](0106-2026-10-21-backups.md)) uses `hsp backup now` and `hsp restore`. From the first release after 1.0.0, the release test also installs the previous release, upgrades it with `hsp upgrade`, checks it, rolls back and checks again. There's no separate test framework for bash (approved by the owner).

## Consequences
- The bundle gains `bin/hsp` and the `hsp-backup` image. The manual steps in `deploy/README.md` become the `hsp install` steps.
- Windows operators use it over SSH. A cross-platform CLI that manages hosts or clusters remotely comes with Kubernetes support ([0104](0104-2026-10-21-v1-release-scope-and-support.md)).
- Disk use grows by about 0.7 GB per installed version until the operator prunes old images. `install.md` explains how.
- `hsp upgrade` and `hsp rollback` are first tested end to end by the release after 1.0.0.
