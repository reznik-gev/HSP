- **Status:** Accepted
- **Refines:** [0054](0054-2026-10-08-release-distribution.md) (the bundle), [0056](0056-2026-10-08-upgrades-and-migrations.md) (upgrades), [0102](0102-2026-10-19-release-workflow.md) (the upgrade test)
- **Refined by:** [0118](0118-2026-10-24-failed-restore-leaves-musical-chairs-stopped.md) (a failed restore), [0119](0119-2026-10-24-recovering-on-a-new-host.md) (recovering on a new host), [0120](0120-2026-10-24-hardware-sizes.md) (disk per release), [0138](0138-2026-11-10-restoring-one-database.md) (restoring one database alone)

## Context
[0054](0054-2026-10-08-release-distribution.md) put an operator command, `bin/musical-chairs`, in the bundle, for installing, upgrading, backing up and restoring. It doesn't exist yet: installing is a page of manual steps in `deploy/README.md`. The owner asked whether it could also run from a Windows workstation that manages Docker hosts or Kubernetes remotely.

## Options considered
The owner chose each of these:

| Question | Options | Chosen | Why |
|---|---|---|---|
| What it's written in | **Thin bash on the host** / Python on the host / a bash shim running an ops container / a cross-platform CLI for remote use | **Thin bash on the host** | It needs nothing beyond what Musical Chairs already requires: Docker with Compose, and a shell. Remote use from any workstation is `ssh host sudo musical-chairs …`. Real logic lives in our Python images. Remote management and Kubernetes come right after 1.0 ([0104](0104-2026-10-21-v1-release-scope-and-support.md)). |
| What the upgrade test upgrades from | **The last release only** / the last release, or the same build until one exists / also from the oldest supported | **The last release only** | 1.0.0 has nothing before it, so the test starts with the first release after it. Before 1.0.0, upgrade and rollback are tried by hand. |
| Old images after an upgrade | Remove all but the previous version / **keep them all** | **Keep them all** | The operator decides when to prune. Each version takes about 0.7 GB of disk. |

## Decision
`bin/musical-chairs` is one bash script, checked by shellcheck, copied into the installation folder by `musical-chairs install`. It runs as root on the Docker host and drives Docker and Compose. Anything with real logic, such as backups, runs inside our images.

| Command | What it does |
|---|---|
| `musical-chairs install <bundle> [--dir /opt/musical_chairs]` | Refuses if the folder already holds an installation. Asks for the public URL and TLS mode, or takes `--public-url` and `--tls` for scripted installs. Checks the checksums, loads the images, writes `.env` and a default `backups.yml` ([0106](0106-2026-10-21-backups.md)), creates the secrets with the right owners, and starts the stack. Then it waits until every service is healthy, and creates the first admin: it asks for a name and email, and prints a one-time password to change at first sign-in. |
| `musical-chairs upgrade <bundle>` | Refuses a downgrade or skipping a MAJOR ([0063](0063-2026-10-08-release-versioning.md)). Then the steps of [0056](0056-2026-10-08-upgrades-and-migrations.md): check the checksums, load the images, take a pre-upgrade backup (abort if it fails), and stop `api`, so nginx answers "being updated". Then migrate, start the new version and wait for `/readyz`. The new `compose.yml` replaces the old one. `.env` keeps every value already set, gains new settings with their defaults, and the changes are printed. The previous compose files are kept for rollback. Old images are never removed. |
| `musical-chairs rollback` | Restores the pre-upgrade backup and starts the previous version's images and compose files. |
| `musical-chairs status` | The installed version, each service's state and health, the last successful backup per schedule and any failure since, and free disk in `MUSICAL_CHAIRS_DATA_DIR` and the backup folder. |
| `musical-chairs backup now` / `musical-chairs backup list` | Run `musical-chairs-backup now` / `list` in the backup service. |
| `musical-chairs restore <backup>` | Asks for confirmation, stops the stack, runs `musical-chairs-backup restore`, and starts it again. |

**Tests:** shellcheck in CI. The release test installs the bundle with `musical-chairs install` instead of the manual steps. The weekly restore test ([0106](0106-2026-10-21-backups.md)) uses `musical-chairs backup now` and `musical-chairs restore`. From the first release after 1.0.0, the release test also installs the previous release, upgrades it with `musical-chairs upgrade`, checks it, rolls back and checks again. There's no separate test framework for bash (approved by the owner).

## Consequences
- The bundle gains `bin/musical-chairs` and the `musical-chairs-backup` image. The manual steps in `deploy/README.md` become the `musical-chairs install` steps.
- Windows operators use it over SSH. A cross-platform CLI that manages hosts or clusters remotely comes with Kubernetes support ([0104](0104-2026-10-21-v1-release-scope-and-support.md)).
- Disk use grows by about 0.7 GB per installed version until the operator prunes old images. `install.md` explains how.
- `musical-chairs upgrade` and `musical-chairs rollback` are first tested end to end by the release after 1.0.0.
