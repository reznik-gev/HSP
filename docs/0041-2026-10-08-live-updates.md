# 0041 — Live updates in v1: polling

- **Date:** 2026-10-08
- **Status:** Accepted

## Options considered
- **Polling** ✅ (v1)
- Server-Sent Events (with Postgres LISTEN/NOTIFY fan-out)
- WebSockets

## Decision
v1 clients learn about changes by **polling through TanStack Query**:
| Data | Policy |
|---|---|
| Lock status of the floor being viewed | Every 15 s, plus on window focus |
| Lock heartbeat (while editing) | Every 60 s, extending the lock ([0016](0016-2026-10-08-edit-concurrency.md)) |
| Published version of the floor being viewed | Every 30 s via a cheap `GET /floors/{id}`. The full plan is reloaded only if `published_version` changed. |
| Seat assignments / search | On focus and after mutations (no interval) |

- Responses for polled resources carry `ETag`s, so unchanged polls return `304 Not Modified`.

## Consequences
- No extra infrastructure or long-lived connections, which suits on-prem reverse proxies.
- Up to ~30 s of staleness for viewers. That's acceptable with admin-only editing in v1 ([0027](0027-2026-10-08-v1-interim-people-and-access.md)).
- Moving to **SSE** later is additive: the same events (`lock.changed`, `floor.published`, `seat.assignment_changed`) can be pushed, and polling stays as a fallback.
