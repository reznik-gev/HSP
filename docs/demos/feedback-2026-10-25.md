## 1. Office moves are a lot of work
**Noted:** the main challenge. Every move means rearranging chairs and desks, moving computers and reassigning seats. Everything that can be streamlined should be. For example, HSP could notice on its own that someone plugged their PC in somewhere else, if the organisation's setup allows it.

**Today:**
- **Seats:** one seat at a time in the app. A seat import from CSV or Excel exists (**Imports**). The API also has a batch endpoint for team moves and swaps, all or nothing, but no screen uses it yet ([0085](../decisions/0085-2026-10-12-seat-assignment-api.md), part 7).
- **Furniture:** the editor has array, auto-numbering and copy and paste across floors ([0049](../decisions/0049-2026-10-08-bulk-layout-tools.md)), and every change is published as a new floor version.
- **Devices:** a device keeps its tag and history when it moves ([0022](../decisions/0022-2026-10-08-device-asset-data.md)). Moving it is a manual edit.
- **Detecting where a PC is:** nothing. HSP reads nothing from the network or from AD.

**Ideas to compare:**
- **A move planner:** pick people or a team, drag them to new seats, see the plan before and after, then apply it all at once. It would use the existing batch endpoint.
- **Devices follow their person:** when someone's seat changes, offer to move the devices issued to them along with it.
- **Detecting location automatically.** Each source depends on how the organisation runs its network:
  - the switch port a PC is plugged into (from network access control or switch logs). This needs the port map from [the first demo's #6](feedback-2026-10-21.md#6-network-ports-and-power-outlets).
  - the computer name an AD sign-in comes from, matched to a device's asset tag.
  - the Wi-Fi access point, which only gives a rough area, not a desk.
  - a QR code on each desk that people scan. This needs no network access at all.

  Any of these should **suggest** a change for an admin to confirm, not change seats by itself.

**To discuss:** which part of a move hurts most: seats, devices, or the furniture? Is a move planner enough for 1.x? Which detection source would a real client allow? It brings HSP closer to network software, the line drawn in the first demo's #6.

## 2. Drawing every floor costs too much up front
**Noted:** building every site, floor and room from scratch is a big initial cost, and makes HSP a hard sell. Find a way to start from what the client already has, such as building plans or architect drawings, scanned or imported.

**Today:** plans are drawn and typed from scratch. There's no background image or PDF to trace over ([0048](../decisions/0048-2026-10-08-no-plan-underlay.md)). Copying one typical floor to the others helps ([0049](../decisions/0049-2026-10-08-bulk-layout-tools.md)). 0048 says to revisit this "if customer onboarding is the bottleneck", and this feedback says it is.

**Options, from cheapest to hardest:**
- **Trace over an image or PDF:** upload a plan as a background for one floor, set its scale with two points of known distance, and draw on top. It's only a reference, not part of the plan's versions. Days of work, and it works with any scan.
- **Import CAD files (DXF):** architects and facility teams often have DWG or DXF files. Walls, doors and even desk blocks could come in as real elements. The results depend on how tidy each file's layers are, so it needs a mapping step ("this layer is walls").
- **Import BIM (IFC):** the cleanest data, with walls, rooms and storeys. Fewer offices have it.
- **Recognise a scanned plan automatically:** an image model finds walls and rooms. The least predictable option, and it still needs review and fixing by hand.

**To discuss:** what do real clients actually have: paper and PDFs, CAD files, or nothing? Start with tracing (cheap, works for everyone), then add DXF?

## 3. Use Material UI
**Noted:** after reading the frontend code, the friend strongly recommends Material UI (MUI) over the plain `div`s and HTML they saw. Plain HTML is harder to maintain and misses much of what React can do. Even for custom styles, MUI's built-in styling would be better.

**Today:** [0066](../decisions/0066-2026-10-08-frontend-state-and-ui-components.md) chose **shadcn/ui** (Radix underneath, styled with Tailwind) over MUI and Mantine. Only 7 of its components are added so far (`frontend/src/components/ui`: alert dialog, button, dropdown menu, field, separator, sheet, tooltip). Layout is plain `div`s with Tailwind classes (about 140 in the app code). A few tables, inputs and a select are still plain HTML. 0066's revisit trigger is many complex tables or forms.

**Two different questions:**
- **Use more ready-made components, whichever library.** The plain tables, inputs and select could become shared components (a data table, a form field, a select), so screens stop repeating markup. This works with today's library.
- **Switch the library to MUI.** That supersedes 0066. MUI brings a big set of finished components (data grid, date pickers, forms) and one theme system. It also costs: rewriting every screen, a heavier bundle, a look that's harder to make our own, and redoing the dark-mode and right-to-left (Hebrew) work.

**To discuss:** is the problem the library, or that we haven't used enough of it? Recommendation to weigh: first replace the plain HTML with shared components on today's library, then decide on MUI with that in hand.

## 4. Frontend file layout
**Noted:** `.ts` and `.tsx` files sit side by side in the same folders. The repository needs a clearer structure, with files and types split better. Global state stores belong in their own place: `sidebarState.ts`, for example, should move.

**Today:** folders follow features (`floors/`, `seats/`, `people/`, `editor/` and so on), and each feature keeps its components (`.tsx`), helpers (`.ts`) and tests together. Client state lives in small Zustand stores, spread over different folders. Three are app-wide: the sidebar's collapsed flag (`app/sidebarState.ts`), the light or dark theme choice (`lib/theme.ts`) and the "session expired" flag (`auth/expiry.ts`). The editor has its own: the plan store (`editor/core/store.ts`), and the save status of an editing session (`editor/session/autosave.ts` and `useEditSession.ts`). Server data lives in TanStack Query, not in stores ([0066](../decisions/0066-2026-10-08-frontend-state-and-ui-components.md)). The layout is described in [frontend/README.md](../../frontend/README.md#layout).

**Options:**
- **Keep feature folders, add rules inside them:** for example a `stores/` folder for app-wide stores, and per feature a `components/` folder and a `*.types.ts` file once it grows.
- **Split by kind across the app:** top-level `components/`, `hooks/`, `stores/`, `types/`. This is simpler to explain, but one feature ends up spread over many folders.

**To discuss:** which layout rules do we want, written into the frontend README? Then move the files in one PR that changes no behaviour.
