# 0040 — Pagination: cursor-based

- **Date:** 2026-10-08
- **Status:** Accepted

## Options considered
- **Cursor-based** ✅
- Offset/limit with totals
- Cursor for large lists, offset for small ones

## Decision
- List endpoints accept `limit` (default 50, max 500) and `cursor`, and return:
  ```json
  { "items": [ … ], "next_cursor": "opaque-string-or-null" }
  ```
- Cursors are opaque, URL-safe base64 values that encode the sort key(s) of the last item plus the filter fingerprint. A cursor reused with different filters returns `400`.
- Default order is by `id` (UUIDv7, so roughly creation time). Endpoints that offer other sort orders (for example people by name) include `id` as a tie-breaker in the cursor.

## Consequences
- Stable, index-friendly paging on large or growing tables (audit log, people).
- No "jump to page N" or total counts by default. Admin tables use infinite scroll or "load more". An endpoint can add an explicit, optional `include_total=true` if a UI really needs a count.
- Small fixed lists (zone types, built-in catalog) may return everything in one page, but use the same envelope.
